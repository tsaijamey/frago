# agent_os — spec

版本：v2（2026-07-22 设计）｜ 状态：已实施（2026-07-23 核实）｜ 前身：v1

最近一次结构性改动：2026-08-10，演员从 frago 扩展后端（人日常浏览器里的一个真实标签）
换回独立无头 CDP 实例。演员落在 **9222**（`-b cdp` 的默认端口，Edge，那份 profile 由 frago
从人真实的 Edge profile 播种，带着现成登录态），机位另占 **9223**。见第 3 节。

同日曾计划把演员挪到 9224 与公用端口分家，**那版没有落地**：分家要求演员自带一份独立的登录态
profile，而唯一能给出这份 profile 的 Chrome 路线被证伪（Chrome v127 起拒绝把调试端口作用于
自己的默认 profile，隔离拷贝里没有登录态）。本文档 2026-08-10 之后仍有若干处按 9224 / Chrome
写的段落，已在 2026-08-11 逐处改回；如再发现残留，以 `broker.py` 与 `recipe.py` 为准。

本文定义 agent_os 的第二代形态。v1 已经跑通并录出成片，v2 不推翻它的架构，
而是把三处结构性缺陷补上：实例身份与运行态混淆、指令以坐标而非语义寻址、
反馈只做到回执级别。

---

## 1. Goal

给 agent 一个属于自己的、可复现、可录制的操作系统画面。

桌面是一个网页，里面有两个应用：虚拟终端 t1、虚拟浏览器 c1。两者的画面来自
真实的 tmux 会话与真实的浏览器标签页——画面里发生的每一件事都真实执行过。
agent 通过一层语义指令操控它，每条指令都返回世界的实际变化；整个过程被录制成
mp4，并留下一份可用于训练的动作日志。

输入：agent 下达的语义指令（移动到某元素、点击、在终端执行、导航、录制）。
输出：桌面画面（供人观看）、mp4 成片、观察-动作-结果三元组日志。

核心价值有两层。对人：演示与教学视频不再依赖真人手动操作，同一份指令重跑一遍
画面完全一致。对 agent：这是一个动作后果可观测、可回放、可积累的环境，产出的
日志是训练特定小模型的干净语料。

## 2. Type & Runtime

type: workflow —— 它编排 UI 资产铺设（agent_os_ui）、broker 进程、浏览器实例、
tmux 会话四个部分，不是单一功能。

runtime: python —— 需要长驻进程、异步 WebSocket、CDP 协议客户端、子进程管理，
这些 shell 做不了，chrome-js 只能活在页面里。

## 3. 架构

```
真实 tmux 会话 ──capture-pane──┐
                              ├─→ broker ──WebSocket /stream──→ 桌面页（UI，纯显示器）
真实浏览器标签 ──screencast────┘        ↑                              ↑
                                  HTTP /control                    机位录制
                                       ↑
                                  aos 短指令入口
```

四个角色，职责不重叠：

**舞台浏览器（演员）** 端口 9222（Edge），无头，常驻。真实执行导航、点击、输入，吐出
screencast 帧。它不占人的屏幕，也不进录像——录的是桌面页，由 9223 机位另行渲染。
这个标签天然的视口多大，画面就多大：broker 一个字都不覆写它，只把这个尺寸读回来
（见下一节）。

演员曾经搬进人日常用的那个浏览器（2026-07-22 至 2026-08-10，走 frago 扩展后端驱动
一个真实标签）。搬回来的直接动因是帧流：**扩展只给前台标签产帧**，演员标签一被切走
画面就停，于是那个标签必须一直被激活着占住人的屏幕——而这块舞台存在的全部理由就是
不占人的屏幕。无头实例没有前台不前台这回事，页面在后台照样合成，帧照产。

**演员为什么留在公用的 9222 上，代价是什么。** 登录态只能有一份好使的：`~/.frago/profiles/edge/9222/`
由 frago 从人真实的 Edge profile 播种（只拷 `Local State` 与 `Default/`，跳过锁文件与日志），
舞台一起来就带着人已经登过的那批站点。撞上登录墙时的接手方式只有一种——人事先在这份 profile
里登好，舞台复用；无头没有窗口，人当场接手那条路不存在。

品牌显式钉死 `--browser edge`，尽管它当前就是默认值：默认值 2026-08-08 从 Chrome 改成过 Edge，
再改一次舞台就会静默换到另一份几乎空白的 profile，而这种错只在撞上登录墙那一刻才暴露。
profile 则**不显式指**——端口推出来的默认目录就是要的那个（9222 → `edge/9222`），
多写一个 `--profile-dir` 只是多一处会漂的重复。

**代价是与公用端口共用，且这个代价是真的。** `-b cdp start` 默认会先杀掉端口上已有的实例再起
自己的，所以别人一条毫无恶意的 `frago browser -b cdp start --headless` 就能把演员连人带登录态
顶掉，换成一份空 profile；broker 的自愈机制会接管新实例里的落地页，`/status` 照报演员活着
——命令、日志、状态三层没有一层报错，只有画面是错的，而这种错只有回看成片才发现。
挡这件事的不是端口，是纪律加提示：`frago browser -b cdp start` 的命令帮助里点名了这条，
book 的 `browser-backend-choice` / `must-browser-fetch` / `must-browser-search` 三章也各写了一句
"起之前先 `frago desktop status`"。

**为什么不干脆挪到 9224 分家。** 试过，不成立（2026-08-10）：分家意味着演员要有一份自己的
登录态 profile，而能给出这份 profile 的只有 Chrome 路线——Chrome Stable 从 v127 起拒绝
`--remote-debugging-port` 作用于自己的默认 profile（反侧载加固），只能用隔离拷贝，
而隔离拷贝里没有登录态：实测 `profiles/chrome/9222` 那 641MB 在 x.com / google.com / reddit
三站全是游客态。于是分家方案连同 9224 一起撤回，白名单收回两个数。

共用 9222 还有一个附带后果要记着：**别人在 9222 上开的标签会出现在虚拟标签条里**，
因为那本来就是同一台实例，没有第二本账。舞台跑着的时候别拿它开新标签。

**扩展后端的采集能力不回撤。** `capture.screencast_start/stop`、`capture.cdp` 那一组
仍在 frago 那一侧完整可用，只是舞台不再走它。

**桌面页（荧幕）** frago server 提供的一个网页，运行在人的浏览器标签里。纯显示器，
不产生任何操作，只负责把两路画面画进虚拟窗口、把虚拟鼠标画在正确位置、上报几何。

**机位（摄像机）** 端口 9223（同样是 Edge），无头。`camera.up`（或 `record.start` 自动
prepare）时才起，对着桌面页收帧交 ffmpeg 编码，`record.stop` / `camera.down` 由
`frago browser -b cdp stop --port 9223` 把整台收走。它必须与演员分开——停录收走的是整台
浏览器，共用端口那一下会把演员一起带走。

**broker** 居中的唯一权威。它是 CDP 客户端、tmux 轮询器、WebSocket 服务器、指令
解析器。所有真实动作从这里发出，所以画面与实际发生的必然一致——这是整个设计的
立足点。

### 端口白名单（MUST）

CDP 端口只允许两个：**9222**（`-b cdp` 的默认值，公用，演员也住在这里）与 **9223**（机位）。
两者必须分开：`-b cdp start` 默认先杀掉端口上已有的实例，而 `stop` 收走整台浏览器——
机位与演员挤在一起，停录那一下就会把演员一起带走，且三层都不报错。

禁止自创任何其他端口——每个新端口都会在 `~/.frago/profiles/<浏览器>/<port>/` 下生成
一个 profile 目录。白名单由 `frago` 的 CLI 层硬校验（`validate_cdp_port`，传别的数
直接拒），hook 规则 `agent-cdp-port-whitelist` 在 PreToolUse 另有一道文字提醒。

浏览器一律经 `frago browser -b cdp start` 拉起，配方不直接起进程、不定义 profile
路径。broker 自己的 HTTP 端口默认 8770。

### 视口：权威在演员，broker 跟随（MUST，2026-07-24 反转）

**尺寸真值住在演员标签自己身上，broker 只读不写。** broker 把这个尺寸读回来，
按它的宽高比决定虚拟浏览器窗口该画多大。跟随的方向只有这一个，反过来没有。
（演员换回无头实例之后，这个尺寸由那台无头浏览器的启动窗口尺寸决定，比"跟着人手
拖动的窗口走"更稳，但读取这条链路一个字都不用改——真值仍然只有一份。）

这条反转掉的是原先的覆写模型：视口曾经由 broker 从荧幕窗口的 content 矩形算出来，
再用 `Emulation.setDeviceMetricsOverride` 覆写到演员标签上。覆写是一次性的，导航、
刷新、debugger 重新附着、target 重建都会把它抹掉，**而没有任何东西会通知 broker**。
为了活下去，那套模型必须再长出三层补救——每个丢失时机主动重放、重放后复核帧尺寸、
帧尺寸对不上就拒推并升级重开帧流。三层全是在给同一个伤口贴纱布。

反转之后那个伤口不存在了：没人下过覆写，就没有覆写可丢。重放、帧尺寸对账、
`stale_frames_dropped`、`viewport_replays` 一并退场。**帧画多大就是演员天然多大，
没有第二个数字可以跟它对账**——真值只有一份，也就没有"两份真值漂移了谁说了算"这个
问题。唯一还需要救的是帧流本身：debugger 一 detach 帧流就停，页面照常工作而画面静止，
所以 detach 仍然触发重开帧流（不是重放视口）。

`Emulation.setDeviceMetricsOverride` 只在**机位**（9223 那台无头浏览器）上保留——
它要按固定的 1920×1080 拍桌面页，那是录制规格，与演员无关。

**不变形是构造出来的，不是校验出来的。** 虚拟浏览器窗口的宽卡在桌面宽的 75%–85%
（1920 桌面即 1440–1632），高由 `H = W / r` 推出，r 是演员视口的宽高比。两边比例相同、
尺寸不等，帧画进 canvas 是纯等比缩放，不变形也不留白。高度装不下时反过来由高定宽，
此时宽允许跌破 75%，回执里注明原因。窗口几何的作者因此是 broker：桌面页收到一条普通
的 `win` 消息照单执行，它只往回报自己量得到的度量（桌面可用区、窗口装饰高度），
不再决定任何尺寸。

因为几何是算出来的，**重放与帧尺寸对账这两件事在设计上就不必要了**——它们回答的是
"演员跟没跟上"，而现在跟随的是虚拟窗口，且是每次读到新视口时同步算的。

`/status` 里对应的字段随之换了一组：`actor_viewport` 是演员天然的视口（就是帧的尺寸），
`aspect_ratio` 是它的宽高比，`viewport_source` 是这个读数从哪条路读来的
（`Runtime.evaluate innerWidth` 为主，`Page.getLayoutMetrics` 为备），`browser_window`
是 broker 据此算出的虚拟窗口几何，含 `width_bounds` / `width_frac` / `height_limited`
与一串 `notes` 说明为什么是这个数字。核对方法是手算 `H = W / r`。

读取的时机是启动一次、导航后一次、切标签一次，覆盖了会变的场合。任何时候想立刻对一次
账，用 `aos viewport refresh`——它重读视口并按新比例重摆虚拟窗口。

`ui_ready` 同属这条链路，语义是**持续状态**而非一次性信号：最近 `ui_live_window_sec`
（默认 3 秒）内有没有收到过帧，也就是"现在画面是不是活的"。一次性的"历史上有没有画出过
首帧"另存为 `ui_first_frame`——主荧幕中途接位后，新主荧幕若早就画过帧就不会再发首帧
信号，用它当开录前的判据会把好画面报成故障。

## 4. 实例模型

### 身份与运行态分离（v2 核心修正）

v1 把两者混在一起，导致 broker 进程一退出，实例身份就消失——而它的物质载体
（人浏览器里那个标签页、viewer 内容目录、clips、tmux 会话）一样没少。实测后果：
kill broker 之后桌面页仍开着却永远收不到画面，且系统无从知道"那里还有一台等着
被喂画面的显示器"。

**身份层**（跨进程、跨会话存活，永不自动删除）

| 字段 | 说明 |
|---|---|
| `id` | 实例标识，默认 `default`；具名实例由人给，kebab-case，**禁止哈希或随机串** |
| `content_id` | 由 `hash(id)` 计算，**不得包含端口** ——v1 用 `hash("agent_os:"+port)`，端口一变桌面页地址就变，人得重开标签页 |
| `desktop_url` | 桌面页地址，因上一条而永久稳定 |
| `clips_dir` | 录制产物目录，跨会话累积 |
| `tmux_session` | 舞台终端会话名 |
| `created_at` | 创建时刻 |

**运行态层**（分钟级，每次启动覆写）

| 字段 | 说明 |
|---|---|
| `pid` / `port` | broker 进程与端口 |
| `status` | `running` / `stopped` |
| `started_at` / `heartbeat_at` | 运行时刻与心跳 |
| `ui_version` | 桌面页上报的资产版本 |

注册表落在 `~/.frago/data/agent-os/instances/<id>.json`。

**stale 处理**：不靠"退出时删"——进程崩溃与机器重启这两种情况本来就执行不到删除
逻辑，指望它清理是设计错误。改为按 pid 与端口探活纠正 `status`。

**"没在跑"与"不存在"是两种状态**，不得都报成"找不到实例"。实例存在但 stopped 时，
入口应明确告知，并可直接拉起——因为身份固定，拉起后仍是同一个 content_id，人的
标签页每秒重连一次会自行恢复，无需任何手动操作。

### 荧幕归属（2026-07-23 实测补上）

身份稳定是有代价的，而代价恰好长在上一段那句"标签页每秒重连一次会自行恢复"上：
标签页不认端口，也不认实例，它认的是一个 WebSocket 地址；而端口不属于身份，所有
实例默认都是 8770。于是旧实例遗留的标签页会连上任何后来的 broker，这不是意外，
是必然。

实测形态：起实例 `miora-design`（content_id `3a1a8b16876f`），人的浏览器里还开着
上一个实例的桌面页 `e1e5664fcf28`。broker 照单收下并接受它上报的 layout，`/status`
显示 `clients: 2`、`stale_clients: []`；broker 按 layout 里的 browser 内容矩形自动
调整舞台视口（当时"窗口多大视口就多大"，视口权威在 broker），于是视口被设成了不属于
它的那块荧幕的尺寸，网页画面只贴在窗口左上角一小块。

（视口那条链路已随上一节的权威反转退场：现在 layout 不再影响演员视口。归属校验本身
仍然必需——外来荧幕上报的度量照样会让 broker 按别人的桌面算窗口几何，而它的 `ready`
拿别人的首帧给自己发合格证这件事，跟视口谁说了算无关。）

**所以连接必须校验归属，而不能靠版本。** uiVersion 那道防线防的是**资产版本旧**，
不是**实例不对**：两个实例的资产版本完全可能相同（本次就是），那时它一个字都拦不住，
双方轮流覆盖 layout，`stale_clients` 还是空的。

落地形态：

- config.json 除 `brokerWs` / `desktop` / `uiVersion` 外，MUST 带 `contentId` 与
  `instanceId`。前者是荧幕地址的依据、broker 拿它比对；后者是人和日志读得懂的名字。
  两个都要——只有哈希的日志没人读得懂，只有名字的比对不成立。
- 桌面页握手第一条消息（`t: "identify"`）自报这两个字段，此后每条 layout 也带。
- broker 收到 layout 时先比 `contentId`，不等于自己的**整条丢弃**，记进
  `foreign_clients`，与 `stale_clients` **分开**——病因不同、补救动作不同，混成一个
  集合会让自检说不清该关哪个标签。外来荧幕的 `ready` 同样不采信：拿别人画出的首帧
  点亮 `ui_ready`，等于用别人的画面给自己发合格证。
- `/status` 的 `clients` 从一个数字改成一张名单，每项含 `contentId` / `instanceId` /
  `uiVersion` / `accepted` / `reason`。理由见第 7 节：反馈要能让人据此决定下一步，
  一个数字答不出该去关哪个标签。

**不改 content_id 的算式，不按实例分端口。** 后者会让桌面页地址跟着端口变，
正好把 v2 好不容易修掉的"端口一变人得重开标签"请回来。

### 主荧幕：同一实例只认一块（2026-07-23 第二层）

归属校验拦得住别的实例，拦不住自己。同一个 contentId 的多条连接，broker 原先
全部照收。实测 `miora-design`：`clients_count: 4`，其中两条 `instanceId` 都是它、
`accepted` 都是 true。两块荧幕各有各的窗口几何、轮流上报，broker 每收一份就按它
resize 一次舞台视口，日志里出现 `1900x868` 与 `1080x606` 来回跳。后果不止是视口跳：
画帧走 letterbox（`fitCanvas` 取 `Math.min`，宁可留空边也不拉伸），帧 1080×606
落进内容区 1900×869 时 k=1.434，canvas 算出 1549×869，左右各留白 175px——
人看到的是"网页没有填满虚拟浏览器窗口"。（这段是覆写模型下的现场。视口那一环已退场，
但多块荧幕轮流上报度量仍会让 broker 反复重算窗口几何，主荧幕这条规则照旧必需。）

多块荧幕是四条各自合理的设计相乘攒出来的：身份永久 → 桌面页地址永久稳定；
`aos up` 的 `open` 默认 true → 每拉起一次开一个标签；`aos down` 从不关人的标签；
桌面页每秒重连且所有实例共用 8770。历史上开过的每一块荧幕只要标签还在都会连回来。
而 `up` 开的标签在**系统默认浏览器**里，扩展的 `list-tabs` 只看得见自己那个浏览器，
所以这些荧幕在 agent 视野里是隐形的。

落地形态：

- **主荧幕 = 同 contentId 里最新连上的那条连接。** 取最新不取最早：人刚打开或刚
  刷新的那个标签才是他正在看的，旧标签往往是忘了关的。主荧幕是**现算**的，不存档，
  所以主荧幕断开时下一条自动顶上，不存在"没有主荧幕"的空窗；接位时 broker 补发一条
  `hello` 逼它立刻重报 layout（UI 收到 hello 就 sendLayout），否则视口会停在
  已经关掉的那块的尺寸上。
- 有资格当主荧幕的，只有**自报过 contentId 且正是本实例**的连接。不认"暂时还看不出
  是谁的"：旧资产标签不带 contentId 且每秒重连，把那段未自报的空窗算进来，它就会
  每秒抢一次主位，几何一秒一跳。资产过旧的标签同样没有资格——它的 layout 本来就被
  版本那条防线丢弃，让它占住主位会导致两边都不报，舞台拿不到任何几何。
- 非主荧幕的 layout **整条丢弃**，`ready` 同样不采信，记进 `duplicate_clients`——
  与 `foreign_clients`、`stale_clients` 并列的**第三个**集合，不合并：foreign 要人去关
  别的实例的标签，duplicate 要人去关本实例多开的标签，stale 要人去刷新，
  三种病因指向三个不同的标签页。
- **帧照发给所有连接。** 非主荧幕只是不能上报几何，不是不能看画面——人可能真的想在
  两块屏幕上同时看。broadcast 不看主不主，这是有意的，不是漏了。
- `/status` 的 `clients` 每项加 `primary`；日志点名
  `实例 X 有 N 块荧幕，认最新连上的那块为主，其余 N-1 块只看不报`，按荧幕格局去重，
  不逐条 layout 刷屏。
- `aos up` 不再无脑开标签：broker 起来后探一次已连着的本实例荧幕，**已有主荧幕就不开**，
  只在返回里给出地址（`screen_reused: true`）。显式传 `open` 的照旧优先。

### 资产过旧的荧幕自己刷新，不必人去关（2026-08-20 加）

版本对不上的荧幕，broker 除了丢弃它的 layout，还会给它发一条 `reload`，它自己
`location.reload()`。这块荧幕是纯显示器，刷新一次什么都不丢——状态全部由 broker 补发。

原先的补救写在自检里：「有旧桌面页标签开着，关掉它」。这条指望人去执行，而人根本认不出
是哪个标签——几个标签地址一模一样、画面也一模一样（帧照发给所有连接）。于是那条 WARN
长期挂着没人处理，而旧资产算几何的方式与新的不一样，它一上报就跟新的轮流覆盖。
能自己好的事情不该写进文档让人记。

每条连接只叫一次刷新：刷新会重连，重连若还是旧版本（中间层缓存之类）就成了死循环。
叫过一次仍是旧的，退回原来那条路——自检点名，人来处理。

**这个机制只能救得了带着它的那一版资产**：更老的标签不认识 `reload` 这条消息，只会静静
忽略。所以引入它的那一次升版，仍要人手动关一次旧标签，此后不用了。

### 荧幕拿到世界状态之前不许上报几何（MUST，2026-08-20 加）

握手的顺序是：荧幕连上 → 自报身份（`identify`）→ broker 把整份现状补发过去（开关、几何、
焦点、鼠标、地址栏、终端缓冲区与视口、最后一帧）→ 补一条 `synced` → **这时荧幕才报第一份
layout**。

在这之前它手上是**出厂状态**：终端窗口 900×560。报上去 broker 会当真——照它把 tmux 会话
resize 成 112×29，等补发的真几何（比如 1160×620）到了再 resize 回 145×32。一来一回两次
SIGWINCH，zsh 每次把提示符重印一遍，旧的那行留在历史里。

实测（2026-08-20）：`tmux resize-window` 来回改一对，缓冲区里就多一行一模一样的提示符
（7→8→8→9）。而录制机位每次 `rec start` 都是新开的一页，于是**每录一段，画面上就多堆一行
重复的提示符**——在只显示最后一屏的年代这些行滚出去就看不见了，有了可回看的缓冲区之后
它们全都留在画面上，滚个七八次屏幕下半截就全是重复的提示符。

报晚几十毫秒没有任何代价；报早的代价是往会话里写垃圾，而且写进去就擦不掉。

## 5. 元素寻址（v2 核心修正）

### 为什么不需要"视觉"

这个 OS 的每一个像素都是自己渲染的：dock 图标是桌面页的 DOM 元素，窗口矩形是 UI
上报的几何，标签条是自己画的，页面元素在舞台浏览器的 DOM 里，终端是 tmux 的字符
网格。位置全部是一手数据。截图加视觉模型是把已知信息渲染成像素再猜回来，慢、不准，
还凭空制造不确定性。系统 hook 同理——hook 用于拦截自己看不见的事件，这里没有
看不见的东西。

正确做法是把已有的位置真值暴露成可寻址的命名空间。

### 命名空间

前缀即域，域决定解析路径：

| ref 形式 | 域 | 真值来源 | 解析方式 |
|---|---|---|---|
| `dock:term` `dock:browser` | 桌面级 | 桌面页 DOM | UI 全量快照 |
| `win:term` `win:browser` `win:term.titlebar` | 桌面级 | 桌面页 DOM | UI 全量快照 |
| `tab:0` `tab:reddit` | 桌面级 | 桌面页 DOM | UI 全量快照 |
| `addr` | 桌面级 | 桌面页 DOM | UI 全量快照 |
| `page:text:文字` `page:css:选择器` `page:"文字"` `page:<裸串>` | 页面内 | 舞台浏览器 DOM | 按需查询 + 坐标换算 |

`page:` 的判型**靠内容不靠引号**（2026-08-27 改）。原来的判据是"这一截首尾是不是
双引号"，它在 JSON 里成立、在命令行上不成立——`--ref page:"文字"` 走一趟 shell，
双引号被吃掉，送到 broker 的是裸串，于是被判成 CSS 选择器，一路报"ref 未命中"。
那句话读起来像"页面上没这个元素"，把排查方向从第一步就带偏。现在四种写法：
`text:` 显式按文字（命令行上安全）、`css:` 显式按选择器（不回退）、引号裹住按文字
（原样保留，既有脚本不用改）、裸串先当选择器解析、解析不成或零命中再当文字。
回退只在**原本必然报错**的位置上生效，所以没有一条现在能跑通的调用因此改变。
判型的唯一实现在 `refs.parse_page_ref` + `broker.page_locate`，`resolve_ref`
（鼠标/点击）、`camera_target`（取景）、`aos` 的 `wait --for` 三条路共用它——
这三处曾各抄一份，漂移的表现是 `mouse to` 找得到而 `camera focus` 找不到。
| `term:r12c40` | 终端内 | tmux 网格 | 字符宽高换算 |
| `term:rows 5-12` `term:rows -8` `term:match "error"` | 终端内 | tmux 画面文本 + 网格 | 行号换算成桌面矩形（**只能取景**） |

**桌面级走全量快照**：元素总共几十个，UI 在每次几何变化时连同 layout 一并上报所有
可寻址元素的矩形。全量优于按需——省掉往返延迟，并让"现在能点什么"零成本可查。

**页面元素走按需查询**：数量成千上万，无法全量。broker 在舞台浏览器执行 JS 按选择器
或文字定位，取得页面坐标，用已握有的窗口内容矩形与视口比例换算成桌面坐标。

坐标换算 MUST 在 broker 内完成。v1 由 agent 手工换算，窗口一动矩形就变，实测出现过
用旧坐标点空的故障。

### 终端画的是缓冲区，不是最后一屏（2026-08-20 加）

终端窗口里那几十行，取自一整块**缓冲区**：tmux 的 history 加当前可见屏。窗口是这块
缓冲区上的一个视口，`term scroll` 决定它停在哪一段。

**在这之前画面上只有最后一屏，而且这不是配置问题，是取数取少了。** pane 有多高由虚拟
终端窗口装得下多少行决定（见"UI 量字符格 → broker resize tmux"那条），所以命令输出一长，
前面的内容必然滚进 tmux 的 history。那份内容一直都在——`history-limit` 默认 2000 行——
只是 `capture-pane -e -p` 不带 `-S` 时只给可见屏，链路从头到尾没人去取。后果是画面上
永远只剩个尾巴：教学视频里一条长输出的前半段观众根本看不到，也没有任何指令能把它调回来。

采集改成两段，各按各的性质取：

| 段 | 怎么取 | 为什么 |
|---|---|---|
| 历史 | 只在它变长时取新增那几行（`capture-pane -S -<新增数> -E -1`） | 历史是追加式的，锚点是 tmux 自己数的 `#{history_size}`。每轮全量重取等于把同样的几千行每秒重抓八遍 |
| 当前屏 | 每轮整段替换（`capture-pane -e -p`） | 它本来就会被就地改写：提示符、进度条、全屏 TUI |

推给荧幕的是增量（`base` / `from` / 变化后的那一段），不是整段：缓冲区上限 4000 行，
整段推的话每秒八次、每次几百 KB，画面还得整块重画，正在回看的人脚下的行会跟着抖。
`history_size` 变小（会话重开、`clear-history`）或改过窗口尺寸（tmux 会重排，历史与
可见屏的分界线跟着动）时整段重取——这两种时刻增量锚点是错的，而错位之后每一帧看起来
都很正常。

**行号基准只有一个：画面上看得见的那一段。** `term:rows` / `term:r<行>c<列>` / `term:match`
一律以视口第一行为第 0 行，与改动前完全一致——贴底时视口就是当前屏，两者重合。缓冲区行号
只出现在 `term scroll` 的回执与错误提示里，且明确标着是缓冲区行号。两套基准混用是这个域
最容易踩空的设计，取景差一行在回执里看不出来。

因此摄像机只认视口：要框的文字在缓冲区里但不在画面上时，`term:match` 报错并点名它在缓冲区
第几行、该发哪条 `term scroll`，而不是照着一个看不见的位置去取景——那正是"回执全绿、画面
是错的"那一类。

**视口的作者是 broker，荧幕只执行（MUST，2026-08-20 反转）。** 视口停在第几行、贴不贴底，
这两个数记在 broker 手上，随 `term.scroll` 下发；荧幕照单摆位，**不拿自己的状态再解释一遍**。
与虚拟浏览器窗口几何同源：真值只有一份。

反转掉的是"broker 读主荧幕上报的 scrollTop 反推行号"那一版。它的错法是这套系统的老熟人：
每块荧幕收到滚动指令后各自拿自己的缓冲区行数和窗口高度去夹、去判贴底，而**录制机位每次
`rec start` 都是新开的一页**——它此刻一行都还没有，目标被夹成 0、还顺手把自己判成贴底，
等快照到了就一路贴回底部。于是成片里终端停在最后一屏，而回执写着它在第 6 行，两边都不算错。

跟着反转的还有三条：

- **新连上的荧幕要补发视口位置**，紧跟在缓冲区快照后面。不补的话它按出厂状态贴底画——
  人正回看着第 20 行，一开机位录下来的却是最后一屏。
- **补发到达时视口容器可能还没有高度**（高度是 `termGrid()` 设的，而它被下面那条 `synced`
  挡在补发之后），此时 `scrollTop` 会被静静夹成 0。所以容器高度一变就重摆一次视口。
- **荧幕报回来的 scrollTop 只当对账**：与 broker 记的差出一行以上就在 `/status` 与回执里
  标 `view_mismatch`。但只在两边看的是同一份缓冲区时才比（比 `bufferLines`）——layout 是
  事件驱动的，缓冲区每 0.12 秒可能长一截，拿旧数字比必然对不上，那是误报，报几次就没人看了。

**贴底是一个状态，不是一次刷新。** 视口贴着底时新输出跟着走（真实终端就是这样）；人一往回
滚就松开，否则回看到一半会被新输出拽回底部。松开状态下 `term run` 的回执带 `view_detached`：
命令照跑、缓冲区照长，而画面停在历史里，这件事不说出来就和"一切正常"长得一模一样。

判"到底了没有"用**行号**不用像素：`scrollHeight`/`clientHeight` 是取整过的，而行高带小数，
两者一减就有半像素出入——滚到底了却算成没到底，此后所有新输出都不再跟着走。

`--to "<文字>"` 的回执 MUST 带 `matched_row` / `matches` / `matched_screen_row`。没有它们，
"命中行摆在窗口中间"这句承诺在回执里无从验证——调用方只看得到一个 `first_row`，判不出
框住的到底是不是它要的那一行，而那正是拿去对镜头的数字。

滚动的**位置**一步到位写进 `scrollTop`，视觉上的移动交给一条 CSS transition。曾经是 rAF
补间逐帧改 `scrollTop`，错法很脏：浏览器判定标签不可见时会冻住 rAF、也会把定时器压到秒级，
补间一帧不跑，滚动静默地什么都没发生而指令返回成功。画面对不对不能取决于哪个标签在前台。

### 终端的三档粒度（2026-07-24 补中间那一档）

终端是唯一一个需要三档粒度的域，因为它同时是"可以点的界面"和"要给观众看的内容"：

| 档 | ref | 拿到的东西 | 什么时候用 |
|---|---|---|---|
| 单个字符格 | `term:r12c40` | 一个字符格（十几像素见方） | 指哪儿点哪儿——鼠标要落到某个字符上 |
| **一段输出** | `term:rows 5-12` / `term:rows -8` / `term:match "error"` | 若干整行组成的横条 | **终端镜头的常用粒度** |
| 整扇窗口 | `win:term` | 整个终端窗口 | 交代"终端在桌面上的位置"这类全景 |

中间这一档才是终端镜头真正要的粒度。教学视频里终端的镜头几乎全是「刚跑出来的那
几行输出」——一条命令的结果、一段报错、一个进度条。两头那两档都表达不出来它：字符
格推到 2.5 倍也只是一小块，没有镜头用途；整窗口推近了等于没推近，观众仍然得自己在
满屏文字里找该看哪里。这一档缺席时只剩两条退路，一条是拿整窗口凑合，另一条是退回
后期裁切——2026-07-24 就是这么翻的车，目测填 crop 参数，摄像机根本没对准要说的位置。

行号一律 **0 基**，与同域的 `term:r<行>c<列>` 共用一套坐标系。同一个前缀下混用两套
基准是最容易踩空的设计：差一位的取景错误在回执里看不出来，只有抽帧才发现。

`term:rows -8` 是最常用的形态。录制时最典型的动作是「跑一条命令，把刚出来的输出推近
给观众看」，而那段输出永远在末尾；绝对行号从上往下数，命令一跑完就漂移，负数形态才
稳定。末尾从**最后一个非空行**往上数：capture-pane 恒把画面补齐到网格高度，不跳过
尾部空行的话框到的多半是一片黑。

`term:match "<文字>"` 更贴 agent 的使用方式——它知道自己在找什么，不知道那东西在第
几行。多处命中取**最后一处**（终端往下滚，最新那次才是刚发生的），并在回执里报
`matches` 总数让调用方知道有歧义；`--context N` 把命中行上下各扩 N 行，因为报错那一
行单独框住往往读不懂，得看见它前面那条命令。

矩形取整行宽（网格左边界 + `cols × cellW`），不按最长行去裁——一段输出天然是整行宽
的，按内容宽裁会让画面左右随行长抖动，一行长一行短镜头就在晃。

行范围超出可见行数时 clamp 到可见范围并在回执里注明，不报错：终端刚启动只有两行时
要求末尾 8 行是完全正常的调用。终端窗口被收起时明确报错并提示先
`window restore --target term`，被关掉时提示 `window open --target term`——两者在 UI
那边上报的都是"不占桌面"的零矩形，对着它取景摄像机会飞到桌面外的虚空，而回执里每个
字段看起来都正常。两条提示分开写是因为补救动作不同，合成一句人会敲错那一条。

区域形态只有 camera 认。`mouse to` 这条路的契约是"一个点"，而区域是一片矩形，形状
不同，不硬塞进同一条路。

### 点击的意图归属

三分判定，与真实窗口系统的命中测试一致：

- 落在浏览器内容矩形 → 转页面坐标，发真实 CDP 输入事件
- 落在终端内容矩形 → 转 tmux 位置
- 落在桌面级元素 → **由 broker 自己执行窗口管理动作**（点 dock 图标即聚焦该程序、
  程序关着就启动它；点标签即切标签）。这与真实 OS 一致：点 dock 是窗口管理器的事，
  不是应用的事。

  **标题栏那三颗红黄绿是纯装饰，点不了。** 这里曾经写着"点关闭即关窗"，那是一句空头
  支票：UI 上报的可寻址元素只有 `dock:*` / `win:*` / `win:*.titlebar` / `addr` /
  `tab:<n>` 五类，红绿灯从来不在名单里，鼠标寻不到它；`desktop_action` 也只认 `dock:`
  与 `tab:` 两个前缀，其余一律回"无点击语义"。照着这句话去做的 agent 会撞墙，而且撞得
  莫名其妙——它连那颗红灯的坐标都拿不到。关窗口走 `window close --target <w>`。

**悬停绑定**：`mouse to <ref>` 之后 broker 记住当前悬停的 ref，`click` 优先按 ref
语义执行而非纯坐标命中。这样一两像素误差不会点空。

## 6. 指令层（aos）

### 入口

配方目录内的可执行：`~/.frago/recipes/workflows/agent_os/aos`。

不进 PATH——往用户环境塞东西是侵入性变更，与"配方不越权"同源。路径是常量，写进
文档一次即可；对训练而言前缀恒定、无歧义、不依赖某台机器的 PATH 配置。

它只做三件事：把短语解析成现有 op、按注册表找到目标实例、POST 到其 `/control`。
broker 协议一条不改。

### 语法约束（为 LoRA 训练服务，MUST）

**同一语义只允许一种写法。** 不做分号串联、不做别名、不做简写——那些是给人的便利，
对模型是噪声：等价形式泛滥会让训练样本形状不一致。

**复用模型预训练见过的语法家族。** 采用 `资源 动词 --具名参数`（kubectl / docker /
gh 同族），微调容量花在学策略而非学语法上。禁止裸位置参数——`cursor 1300 420 700`
这种形态靠位置携带语义，模型需记住"第三位是毫秒"这类脆弱约定，且新增参数会使历史
样本全部作废。

**动词自带意图。** 有目标的移动与无目标的闲晃用不同动词，而非同一动词的两种参数——
模型不必靠参数形态反推意图，两类样本分布天然分离。

### 开关程序（2026-08-10 加）

在这之前，这个 OS 里的程序**关不掉**。终端和浏览器根本没有关闭这个动作，最接近的
`window min` 只是收进 dock（程序还在跑、dock 的灯还亮着）；唯一关得掉的是图片浏览器，
而它走的是自己那条 `image close`。于是同一件事有两套语义，其中一套只对三个程序里的
一个成立——想录一段"演示完把终端关掉、只留浏览器"的镜头就演不出来。

现在三个程序共用一条路：

| 指令 | 画面上发生什么 | dock |
|---|---|---|
| `window close --target <w>` | 窗口原地缩一点淡出，离开桌面 | 灯灭 |
| `window open --target <w>` | 窗口淡入回来并置前台 | 灯亮 |
| `window min --target <w>` | 窗口飞进 dock 图标 | 灯还亮着 |
| `window restore --target <w>` | 从 dock 飞回来 | — |

**close 与 min 在画面上必须一眼分得开**，所以两者的动画刻意不同（缩放淡出 vs 飞向
dock），dock 的圆点是第二个信号。圆点的语义随之改成"这个程序在不在跑"（macOS 就是
这样），前台那个再亮一档——此前它只表示"哪扇窗口是前台"，于是开着的程序反而没有
任何标记。

**关掉不动载体。** tmux 会话照常在跑、演员标签照常在收画面、已经装进图片浏览器的那张
图留着，所以 `window open` 回来的是原样。杀掉它们在画面上看不出任何区别（观众只看到
窗口没了），代价却是真的：跑了一半的会话没了、重新拉起要几十秒。回执里的
`carrier_kept` 明说这件事，免得下一个人去查一个根本没发生的"会话被杀"。

**指向某个程序的动作会把它重新打开**，与 `ensure_active` 自动置前台同源：`term run`
打在一个关掉的终端上，正确结果是终端回来并执行，不是报一句"你得先打开它"。发生了就在
`effect.launched` 里说出来。要拍空桌面，不发这类指令即可。

**三个都关掉是合法状态**，此时 `focus` 为 `null`、菜单栏退回 Finder。键盘输入在这个
状态下没有接收方，`type` / `key` 明确报错而不是往空处送——不拦的话字会被送给一扇不在
桌面上的窗口，命令看着成功而画面什么都没发生。

`/status` 与 `elements` 都带 `windows_open`。与 `content_rects` 分开报：那边关掉的程序
是个 `null`，看不出是关了还是收起来了，而两者的补救动作不同（`window open` vs
`window restore`）。

### 窗口词的语义（2026-07-24 改）

`--target browser` 的三个动词不再是"摊满/还原"这种窗口管理器的语义，它们选的是宽度：

| 指令 | 宽 | 高 |
|---|---|---|
| `window max --target browser` | 桌面宽的 85%（1920 桌面即 **1632**） | `W / r`，r 取演员视口的宽高比 |
| `window restore --target browser` | 桌面宽的 75%（即 **1440**） | 同上 |
| `window move --target browser --w <n>` | `<n>` 夹进 1440–1632 | 同上，**不接受调用方给的 `--h`** |
| `window min --target browser` | 收进 dock，与几何无关 | — |

高度永远是算出来的，不是给的：给了高就等于给了一个跟演员视口不同的比例，画面要么变形
要么留白，而这两样正是这套设计要消灭的东西。桌面可用高装不下时由高定宽，宽会跌破 1440，
回执的 `notes` 里写清楚是被高度限制了——回执里说不清为什么是这个数字，下次有人看到 1400
就会以为是 bug。终端窗口不受这套约束，它照旧把意图交给 UI 算。

**`split` 已退场。** 对开要把浏览器压到半个桌面宽（约 950），与"恒占 75%–85%"直接冲突；
两条规则无法共存，留下后者——半宽的浏览器要么违反下界，要么就得放弃与演员视口同比例，
而同比例是这套设计的全部意义。

### 运镜词的语义与三档反馈（2026-07-24 加）

`camera` 管的是**摄像机**——取景框对着桌面的哪一块；`window` 管的是**被摄物**——虚拟窗口
在桌面里多大、摆在哪。两者都会改变"元素在成片里有多大"，但改的是完全不同的东西。取景只
作用于录制落盘的帧，桌面页上人看到的画面不变，所以不录制时 `camera focus` 是一条纯预演
指令：它照样算出构图，让调用方在开录**之前**就发现这个元素在 2 倍下没法居中。

倍率钳在 1.0–2.5。下限是几何的，1 倍就是整个桌面，再缩只有黑边；上限是清晰度的，桌面页
按 1920×1080 渲染，3 倍等于把 640×360 的真实像素拉满全屏，信息量不增反减。想要更清晰的
特写得让虚拟浏览器窗口本身更大让页面重排，那是录制前的事。

`--ref` 可以给多个，取所有目标的外接矩形。旁白说"装机量最高的这几个"时要的是好几张卡并排，
按单个 ref 取景就是错的——镜头会怼在第一张上，而观众听到的是"这几个"。多目标时 `--zoom`
退化成**上限**：装不下所有目标的倍率没有意义，实际取的是外接矩形（含 40px 安全边距）能装
下的最大倍率，回执里 `zoom_fit` 与 `zoom_note` 会写清楚。

回执分三档：

| 档 | 判据 | 语义 |
|---|---|---|
| 居中 | `centered: true` | 目标落在画面正中 |
| 贴边受限 | `centered: false` + `clamped` + `offset` | 目标在画面内，但没能完全居中 |
| 出框 | `ok: false`（CameraError） | 倍率太高，或目标本身比取景框还大 |

**贴边算成功。** 元素靠近桌面边缘时取景框移到边界也无法让它完全居中，但画面确实拍到了、
构图可用，报成失败会逼调用方处理一个不用处理的情况。反过来，静默居中失败更糟——那正是
2026-07-24 翻车的模式：以为对准了，实际没对上。所以 `clamped` 明说夹在哪几条边，`offset`
明说差多少像素，两个字段合起来让调用方自己判断这一镜要不要重构图。

`clamped` 恒为数组，不因为只夹了一条边就退化成字符串：角落里的元素真的会同时夹住两条边，
只报一条是撒谎；而同一字段一会儿是字符串一会儿是数组，正是本节语法约束要挡的那种形状不
一致。回执里刻意**不提供** `min_zoom_centered` 这类"提高倍率就能居中"的建议：数学上成立
但结论荒谬——左贴边元素要推到 5.33 倍才能居中，那时取景框只剩 360×203，上下文全切掉，
画面还糊。贴边元素的正解是让它别贴边：把虚拟浏览器窗口挪到桌面中间，或滚动页面让元素落到
视口中部，然后 1.5–2 倍就够。

### 动作自动激活目标窗口（MUST，2026-07-24 加）

**规则：任何指向某扇窗口的动作，都自动把该窗口置为 active；active 窗口恒在最上层。**

| 动作 | 激活 |
|---|---|
| `mouse to --ref`（ref 落在页面里） | browser |
| `mouse to --ref`（ref 落在终端里） | term |
| `mouse to --x --y`（纯坐标，没声明目标） | 不改焦点 |
| `browser open` / `scroll` / `read` / `click`，`elements --in browser` | browser |
| `tab open` / `switch` / `close` | browser |
| `term run` | term |
| `type` / `key` | 当前 active 的窗口（键盘本来就送给前台，这里恒是 no-op；三个程序全关掉时明确报错，不往空处送） |
| `camera focus` / `camera pan`，ref 落在页面里 | browser |
| `camera focus` / `camera pan`，ref 落在终端里 | term |
| `camera reset` | 不改焦点——它回的是整个桌面，不指向任何一扇窗口 |
| `wait`、`term read` | 不改焦点，见下 |

**为什么必须是自动的，不能靠调用方记得先发 `focus`。** 2026-07-24 录 twitter 时
`camera focus --ref page:"Explore" --zoom 1.8` 的回执全绿——`ok: true`、
`target_in_frame: true`、`clamped: ["left","top"]`、几何一个数字都没错——而抽帧一看，
画面里推近框住的是终端窗口，x.com 的侧栏压在它下面。实例起来后焦点默认是 term，
整段录制里发的 `browser open` / `elements` / `camera focus` 没有一条会改焦点，
终端就一直压在上面。

`camera` 对准的是"元素在桌面坐标系里**应该**在的位置"，它没有、也不可能有"那个位置现在
显示着什么"这个信息，所以这类错误在回执里一个字都看不出来，只有录完抽帧才发现，那时现场
早没了。凡是"漏发一条指令就静默拍错、且只能事后从成片发现"的东西，都不该留给纪律。

实现是 broker 里唯一一条 `ensure_active(win)`，所有指向窗口的 op 进来先过它，不在各个 op
里散着抄 `if win != stage.focus`——散着抄正是这次一口气漏掉 navigate / exec / type /
camera.focus / camera.pan 五处的直接原因。`focus` 保留为显式动词（人明确要换焦点时用），
`ensure_active` 是它的幂等封装：已经是 active 就 no-op，不广播、不产生多余的 layout 上报。

**激活如实回报，绝不静默改状态**：发生了就在 `effect` 里带 `focus: {before, after}` 与
`focus_changed`，调用方要能从回执看出"我这条指令顺带把窗口提到了前面"。

**目标程序关着时，`ensure_active` 顺手把它打开**（2026-08-10 补）。理由与自动激活同源：
`term run` 打在一个关掉的终端上，正确结果是终端回来并执行。启动比换焦点动静大得多——
画面上多出一扇窗——所以单列 `effect.launched`，不混在 `focus_changed` 里。

**鼠标移动也算"指向窗口的动作"（2026-08-04 补）。** 上面那句"散着抄漏了五处"当时还漏了
第六处：`cursor`。它当时看起来像纯粹的画面动作、不指向任何窗口，于是没挂 `ensure_active`。

漏掉它的表现和当初那次一模一样——回执全绿、画面是错的。判断鼠标落在哪扇窗口用的是层级
顺序，浏览器被终端压着时，指向浏览器元素的坐标会被判成 term，于是悬停不转发给真实浏览器：
菜单不展开、按钮不高亮，而回执里只写着 `win: "term"`。

靠后面那步 `click` 补激活不够：`browser click` 在 aos 里恒被编译成 `cursor` + `click`
两条，激活挂在 `click` 上意味着鼠标先当着镜头从错误的窗口上划过去，窗口在按下的瞬间才跳到
前面。所以激活必须发生在**移动之前**。

判定用哪扇窗口沿用 `target_window(ref)`（与 camera 同一条），不看坐标——坐标恰恰是被层级
污染的那个量。纯坐标移动（`--x --y`）没有声明目标，不改焦点。

**观察类指令例外。** `wait` 与 `term read` 是"看"不是"做"：盯一个还没出现的元素时反复翻
窗口层级，录进片子里就是一段没人下过的指令。`wait` 的探针（走 `elements` / `exec`）因此
带 `observe: true`，broker 见到它就不激活；`term read` 直接读 tmux，根本不经过 broker。

### 开录门禁（MUST，2026-07-24）

`rec start` 在真正开录之前逐项体检，任何一项不成立就**拒绝开录**并返回 `ok:false`
（HTTP 409），载荷里给 `gate`（每条含 level / item / detail / means / if_ignored /
how_to_fix，与 health 自检同构）与 `how_to_fix` 列表。

| 判据 | 不满足时录下来是什么样 |
|---|---|
| 本实例荧幕有且仅有一块 primary，无重复客户端 | 多块荧幕轮流覆盖布局，几何来回跳 |
| tmux 会话存在（`capture-pane` 取得到内容） | 终端窗口全程空白，只有 broker.log 在刷 capture-pane 失败 |

**曾经有四项，撤掉了两项**，理由不同：

`viewport_matches_window` 随视口权威反转一并作废。它问的是"演员视口跟不跟得上虚拟
窗口"，那是覆写模型下才成立的问题；现在虚拟窗口的形状是按演员视口的比例算出来的，
两者同比例是构造出来的而不是校验出来的，这条判据恒为真——一条永远通过的闸门不是
防线，是噪声。

`ui_ready` 撤于同日，理由是它把正当镜头误判成故障。它问的是"最近 3 秒有没有新帧"，
而静止的网页本来就不产帧；想拍一个不动的界面是完全正当的镜头，此刻画布上挂的帧没有
骗人，只是没在动。拿它当开录判据等于禁止静态镜头。冻帧那类真故障改由 `rec stop` 的
`unique_ratio` / `frozen_tail_sec` 事后抓——那两个数分得开"没在动"和"该动却没动"，
开录前分不开。`ui_ready` 仍留在 `/status` 与启动自检里，那里它是信息，不是闸门。

**为什么剩下两项是硬拒绝而不是警告。** 它们的共同形态是：指令全部生效、回执全部正常、
`/status` 一切正常，只有画面是错的。警告在这种形态下没有作用——它出现在开录那一刻的
输出里，而人和 agent 此时正忙着往下走脚本，等发现不对已经是二十分钟后看成片的时候，
那时素材已经废了，重录的成本是整段重演。拦在开录前的代价只有几秒钟。这两条纪律在
2026-07-23/24 那次拍片会话里各被违反两次，其中一次就发生在 agent 刚写完反省之后：
散文形态的纪律靠自律执行，自律不可靠。能被代码拦住的，不要写进文档靠人记。

错误信息 MUST 给出可直接抄的修复命令，而不是只说哪里不对。抄不动的场合（比如就是要
拍故障现场）用 `rec start --force` 显式绕过：绕过后回执带 `gate_bypassed` /
`gate_bypassed_detail` / `gate_note`，broker.log 同时写一条 ⚠️ 记录。**绕过留痕，
不许静默**——事后回看成片发现构图不对时，要查得到当时是知情放行的。

停录侧对称地补上事后证据：`rec stop` 自动从成片按时长百分位（8/25/42/58/75/92%）抽
6 帧拼成 2×3 宫格 `<name>-contact.png`，并给出 `total_frames` / `unique_frames` /
`unique_ratio` / `effective_fps` / `frozen_tail_sec`。去重比值是冻帧故障最早的可见
信号，比人肉眼看宫格更早；`frozen_tail_sec` 超过 3 秒在回执里标 warn。抽帧与去重全部
交给 ffmpeg（mpdecimate / freezedetect / scale+stack），不在 Python 里逐像素循环。
自检恒不抛异常——诊断出错不得让停录失败，片子已经录好了。

**批量模式**：从标准输入读，每行一条，顺序执行。时序精度由 broker 内部保证，与调用
进程次数无关；这也让长路径前缀只出现一次。单条模式用于探索与调试。

### 坐标的定位

`mouse drift --x --y` 保留，但语义上明确是"自然随意的移动"——录制时鼠标轨迹要走得
像人，那时才需要绝对坐标。它不参与操作语义。

理由：像素坐标是坏的训练信号。教模型"点在 (1300, 420)"没有泛化价值，换个窗口尺寸
或页面版本立刻作废；教模型"点击文字是 recipes 的按钮"才可迁移。训练样本因此天然
分成两类——语义层教策略（主体），坐标层只教"怎么把鼠标演得像人"（仅录制场景）。

## 7. 反馈（v2 核心修正）

原则早已确立：**每条输入指令必须获得 feedback**。v1 没有违反它，但降级执行了——
实现成了回执而非反馈。回执证明指令发出去了，反馈证明世界变了。

事实分三级，v1 把它们混成一级（`clicked: true` 只表示事件已发出，不表示点中了什么、
页面有没有反应，实测点空时回执依然是 `true`）：

| 级别 | 含义 | v1 | v2 |
|---|---|---|---|
| L1 受理 | 指令已收到 | ✅ 唯一有的 | 保留 |
| L2 接受 | 动作命中目标 | ❌ | 必须（击中了哪个 ref） |
| L3 生效 | 世界状态改变 | 仅 navigate 有 | 必须（前后差异） |

**何时响应**：效果落定即返回，而非发出即返回。`navigate` 已经在做（等 load 且等新帧
到达），把它抽成通用能力。这条立住后 `sleep` 大面积消失——v1 中那些猜出来的等待
时间，本质是在补偿反馈来得太早。

**如何响应**：与因果链对齐。指令想改变什么就回报什么的前后状态——点击回报击中了谁、
页面有无变化；输入回报目标窗口收到了什么；导航回报最终 URL 与标题。回可验证的差异，
不回笼统的成功标志。

**颗粒度**：默认回**变化摘要**（URL 变没变、帧变没变、命中了哪个 ref、终端新增几行），
细节显式索取。判定标准是"能否据此决定该不该往下走"。全量 DOM 快照会淹没信号。

## 8. 动作日志即训练样本（v2 核心修正）

v1 的 `clips/<name>.jsonl` 只有动作与时间戳，是流水账。补齐后每条应是完整三元组：

```json
{
  "at": 12.34, "until": 13.04,
  "observation": {"refs": ["dock:term", "page:\"recipes\"", "..."],
                  "url": "http://...", "focus": "browser"},
  "action": {"verb": "mouse.to", "ref": "page:\"recipes\""},
  "result": {"hit": "page:\"recipes\"", "url_changed": false, "frame_changed": true}
}
```

缺了 observation 那一半，模型只能模仿动作序列，学不到"为什么在这一步选这个动作"。
这件事越晚做，积累的残缺日志越多，且**补不回来**——观察是当时的现场，事后无法重建。

## 9. 启动自检

启动时输出一份结构化健康报告，只报会静默出错的项，每项带阈值判定，够格才标 WARN：

| 检查项 | 判定 |
|---|---|
| clips 体积与段数 | 超阈值标 WARN |
| CDP 端口是否落在白名单 | 越界即 WARN |
| 残留 CDP 实例与孤儿 profile 目录 | 存在即 WARN |
| 桌面页 URL 与上次是否一致 | 变化即 WARN（人需重开标签页） |
| 是否有不属于本实例的荧幕连着 | 存在即 WARN（点名是哪个实例、要人关哪个标签） |
| ui_ready 是否达成 | 未达成即 WARN |
| tmux 会话是否真的存在 | 取不到画面即 WARN |

七项全部真实出过事：`screen_ownership` 是 2026-07-23 实测暴露的，`tmux_session` 是
2026-07-24——`aos down` 在 broker 已失联时返回 `None` 且没真停，下一次 `up` 复用了半死
的 broker：它连着端口、能应答 status，却从没走过建 tmux 会话那步，于是终端永远空白。
`ui_ready` 只反映浏览器画面帧、不管终端，所以 `/status` 完全看不出来。其余在 v1 阶段。

**给 agent 的提问必须可行动**（actionable diagnostics）。不写"是否有风险"这类开放式
提问——开放式问题换来的是敷衍的"无风险"。应写成带判定条件的强制回答：凡有 WARN，
agent 必须逐条说明是否影响本次任务、选择处理还是接受，说不出理由不得继续。
约束长在动作上，不长在措辞上。

## 12. Error Scenarios

| 场景 | 处理 |
|---|---|
| 本机无 tmux | 明确报错并终止——舞台终端无法启动 |
| 本机无 ffmpeg | 录制指令报错，其余功能不受影响 |
| 启动那十几秒里被人查了状态 | 端口那时是**绑上了但还没开始 accept**（lifespan 要建 tmux、拉演员浏览器、开帧流），而 `registry.read_instance` 的判据是"pid 活着**且**端口可达"，于是它按规矩把记录纠正成 stopped 并清掉 pid——几秒后 broker 好端端地在服务，却再没人把记录改回来，之后每条指令都被"实例存在但没在运行"挡掉。补救不在 read_instance（它那条判据是对的，专治卡死的 broker），而在 broker 这一侧：**开始服务之后再把"在跑"落一次盘**（2026-08-20 加） |
| 注册表里的 pid 被清空过 | `frago desktop down` 手里就没有可以 kill 的东西了：它改完记录就走，老 broker 照跑，下一次 `up` 探到端口活着直接复用它——**改完代码怎么重启都还是老进程在服务**，而两边都不报错。所以 `/status` 自报 `pid`，`down` 在注册表没有 pid 时问它要；且 `down` 不再要求实例"正在运行"才肯执行——停一台还在应答的 broker 不该被一句记录挡住（2026-08-20 加） |
| broker 端口已被占用 | 探活 `/status`：是同实例则复用，非本实例则报错，**不再起第二个**。探活挡不住同时起两个（`frago desktop up` 与守护几乎同时看到"没人在跑"），所以真正的分胜负点是**先绑端口再建舞台**：绑上了才走 lifespan，绑不上一个字节都不碰就退场。2026-08-20 补——在这之前 uvicorn 是先跑 lifespan 再绑端口，输的那个已经把 tmux 会话建好（顺带 kill 掉赢家那个同名会话）、注册表改成自己的 pid，才在绑定时失败，退场时又按流程收走会话；结果赢家活着、端口照应答、`/status` 全绿，而终端窗口全程空白，只有 broker.log 每 0.12 秒刷一条 capture-pane 失败 |
| 舞台浏览器未能就绪 | 报 `frago browser -b cdp start` 的原始错误，不吞 |
| 页面静止导致零帧 | 开流与导航后各助推一次重绘逼出首帧（v1 已实测：不推则首帧永不到达，桌面上浏览器窗口一直空白且无任何报错） |
| 新客户端连上时尚无帧 | 补发快照；若 `last_frame` 为空则重启帧流 |
| `ref` 解析不到元素 | 返回明确错误并附当前可寻址元素列表，**不静默失败**、不退化成坐标点击 |
| 点击落在任何窗口之外 | 明确报告"落空"，不伪造成功 |
| 桌面页资产版本与 broker 不符 | 明确告警要求刷新，不让指令静默失灵 |
| 目标站点反爬拦截 | 如实返回被拦页面（v1 实测 reddit 会拦无头浏览器）。演员是无头实例，没有窗口给人当场接手；补救路径是人事先用 `frago browser -b cdp` 在 9222 那份 profile 里登好，舞台复用它 |
| 录制期间无帧 | 报错并保留帧目录供复查，不产出空文件 |

## 13. Test Cases

**T1 实例身份跨进程稳定**
```
aos up --id default            # 记录 content_id
aos down
aos up --id default            # content_id 必须一致，桌面页无需换地址
```
验证点：两次 `content_id` 相同；`down` 后注册表条目仍在且 `status: stopped`。

**T2 语义寻址点击**
```
aos elements --in browser --text recipes
aos mouse to page:"recipes" --ms 700
aos mouse click
```
验证点：click 回执含 `hit: page:"recipes"` 与页面变化证据；agent 全程未接触任何坐标。

**T3 反馈级别**
```
aos mouse to win:browser --ms 300      # 移到空白处
aos mouse click
```
验证点：回执必须表明未命中任何可交互元素，**不得返回笼统成功**。

**T4 语义等待取代 sleep**
```
aos browser open https://example.com
aos wait --for page:"Example Domain" --timeout 15
```
验证点：`wait` 在内容出现后立即返回并报告实际耗时；整个流程零 `pause`。

**T5 端口白名单**
```
aos up && frago browser -b cdp status
```
验证点：舞台跑着时 9222 上是一台无头 Edge（演员）；架机位后额外出现 9223，`rec stop` 后消失；
`~/.frago/profiles/edge/` 下不得出现 9222 / 9223 以外的目录。**反向验证**：舞台跑着时执行
`frago browser -b cdp start --headless`，演员会被顶掉——这是已知代价，不是回归，见第 3 节。

**T6 日志三元组完整**
```
aos rec start --name t6 && aos mouse to dock:term && aos mouse click && aos rec stop
```
验证点：`t6.jsonl` 每条记录同时含 `observation` / `action` / `result` 三个字段。

## 15. 不做什么

**不做视觉识别。** 位置是一手数据，不经像素绕一圈。

**不做系统 hook。** 没有看不见的事件需要拦截。

**不在 frago core 加命令组。** 操控入口属于配方，随配方升级与删除。

**不引入 xterm.js。** `capture-pane -e` 给的是带 SGR 转义的纯文本，而且颜色码**逐行
自闭合**（实测：每行自己开、自己关），所以按行渲染不会丢色，一百行的 ANSI→HTML 转换足够。
外链 CDN 在离线时不可靠，把第三方产物塞进资产目录不划算。

2026-08-20 把终端改成可回看的缓冲区时重新掂过这件事：xterm.js 自带 scrollback，看着正好。
不换的理由是这块画面的需求与它的强项不重叠——这里没有真实输入要处理（荧幕对键鼠完全免疫），
要的是"按行号换算成桌面矩形"这种它并不提供的能力，而它自带的滚动条会占掉宽度让字符列数
抖动。换过去要写的胶水比现在这一百行多。

**不因为舞台不用了就回撤 extension 的采集能力。** `capture.screencast_start/stop`、
`capture.cdp`、`capture.record_start/stop` 与 `record_tab` 是演员搬进人浏览器那段时间
（2026-07-22 至 2026-08-10）加出来的，实现完整、实测通过，现在仍在 frago 那一侧可用。
舞台换回 CDP 后端只是不再走它，不是判它没用——录人真实浏览器里那个已登录标签，
除了它没有第二条路。删掉再要用就得重写一遍，而重写出来的不会比现在这份更好。

## 16. 实施顺序

六项已全部落地，2026-07-23 逐项核实：注册表分层见 `instances/<id>.json` 的身份/运行态两组
字段；`aos elements` 与 broker 侧 ref 解析在用；点击回执含 `hit`；`aos` 词表与下文一致；
`clips/*.jsonl` 每条含 observation / action / result 三元组；启动自检在 `health.py`。
下面保留原始排序理由，供后续改动时参考。

1. **注册表与身份固定**——其余各项的地基（`content_id` 去端口化、身份/运行态分层、
   stale 探活）
2. **元素寻址**——UI 全量快照上报、broker 侧 ref 解析与坐标换算、悬停绑定
3. **反馈升级**——三级事实、效果落定即返回、变化摘要
4. **aos 入口与词表**——短指令解析、实例寻址三档、批量模式
5. **日志三元组**——observation 与 result 落盘
6. **启动自检**——依赖注册表就位后才有东西可查

第 5 项虽排在后面，但它是唯一**数据补不回来**的一项：每晚一天就多录一批残缺样本。
若要调整顺序，优先把它提前。
