# better-recipe-gate

分类: 偏好（BETTER）

干完一段活、或者正要往临时目录写一个能跑的脚本时，先过这道闸：这段劳动该不该留下来。默认答案是不留——闸是用来挡的，不是用来放的。

## 为什么需要这道闸

agent 每个会话都是第一次。这句话不是修辞：判断「这活我以前干过」需要跨会话的记忆，而这恰恰是单个会话拿不到的东西。结果是每次都干净利落地干完、把成果扔掉、下次从头再搭一遍。

系统里所有提醒都在管「把这一次做对」——改完要验证、别截断读取、脚本用 uv run。没有一条在管「下次不用再做」。这道闸补的就是那一条。

## 五问，有先后，任一不过就停

**一｜会不会再来一次，凭什么这么说。**

「我觉得还会用到」不算证据。算证据的只有三种：用户明说了会重复；执行记录里同类的活干过好几遍；这活本身有周期（每次发版、每周一次、每次改完某类文件）。

第一种最可靠。第二种自己判断不了，要去数据里查。第三种看这活是不是挂在某个固定事件上。

三种都对不上，到此为止，不必问第二问。

**二｜流程能不能事先写死，要动脑子的地方能不能关进固定的工位。**

拆成两小问：步骤的顺序和分支是不是事先确定的（不是每次现场决定）；每个需要判断的地方，进什么、出什么形状，能不能事先规定。

两个都是，就该做成 recipe——哪怕中间有三个工位都在调模型。撰写文案、打分、分类、总结，这些都必须动脑子，但都可以是流水线上一个位置固定的工位。

流程本身要现场决定，那是 skill，不是 recipe。硬做成 recipe 等于把不确定性焊死在代码里，跑出来的东西比不做更危险。

**三｜变的部分能不能收成有限几个参数。**

不能，说明抽象层次找错了。往往是把两三件事捆在了一起，拆小之后各自都能过闸。

**四｜它依赖的外部东西稳不稳。**

依赖第三方接口、页面结构、别的命令的输出格式，这些都会变。不稳不等于不做，但要当消耗品对待：在 recipe 里写明它靠什么活着，坏了先查那里。已经翻过车的类型有三种——上游命令的返回格式变了、脚本里埋了只在某台机器成立的路径、用户期待和实现悄悄分叉。

**五｜跑错了代价多大。**

recipe 是不看着跑的。会删数据、会给外部发消息的，要么加一道确认，要么干脆不自动化。

## 反向的闸：五问全过，仍然不该做的三种

已经有 frago 命令能干的，别再包一层。工具优先级里 recipe 排在 frago 命令前面，意思是有 recipe 就优先用 recipe，不是说什么都该做成 recipe。

只在这一台机器上成立的，不做。

价值在于「怎么判断」而不是「做了什么」的，不做——那种东西该沉淀成知识。

## 重复的东西该去哪

| 重复的是什么 | 落点 |
|---|---|
| 什么时候该想起什么 | `frago hook-rules add` |
| 事实、结论、踩过的坑 | `frago <domain> save` |
| 一串确定的动作 | recipe |
| 判断的方法 | book 条目 |

「重复工作流→recipe」这句话把四条压成了一句，压掉的正是分辨它们的能力。

## recipe 到底省下什么

不是省推理。这台机器上三十多个 recipe 在运行时要调模型或派 agent，包括视频生产、会议助手、盘中决策这些主力流程。

省的是「决定怎么做」那部分推理，以及它带来的漂移。同一件事让 agent 做十遍，会得到十种略有不同的做法，其中几遍漏步骤、几遍自作主张加东西。做成 recipe 之后，流程这一层的方差归零，方差只剩在那几个被规定的格子里，格子的进出形状还被约束着。

真正买到的是可重现，不是省钱。所以越是要交付给人看的东西，越该走 recipe——人不能接受「这次和上次做法不一样」。

## 过闸之后

判定该做，就当场做，不要留待办。做的规范看：

```bash
frago book recipe-spec-writing   # 需求怎么写成 spec
frago book recipe-creation       # spec 怎么变成 recipe
frago book recipe-fields         # 元数据字段
frago book recipe-authoring      # 脚本怎么写
```

判定不该做，一句话说明卡在第几问，然后继续原来的活。

## 下次召回入口

```bash
frago book better-recipe-gate
```

往临时目录写可执行脚本时自动注入本条。
