# frago-principle-recall

分类: 第一性原理（MUST）

## 解决什么问题

你每次启动都是零记忆，而且训练数据里没有这台机器、这个人、这套流程的任何事实——ali 是干什么的、那个 recipe 上次为什么改、用户三个月前否掉过哪个方案，一条都没有。

碰到不懂的，你的默认动作是**读代码加推理，拼一个看起来对的结论**。这个动作在通用编程里成立，在 frago 里几乎必错：用户问的极少是"这段代码怎么跑的"，而是"我这儿是怎么做的"。后者的答案不在代码里，在这个用户积了几个月的会话、产出和知识域里。

代价不是慢。代价是用户得花两三轮把你否掉，而你每一轮还是从零再猜一遍——因为你压根不知道有东西可查。

## 第一性原理

**不知道就先召回，NEVER 先推理。**

**代码告诉你机制，历史告诉你选择。用户问的几乎总是选择。**

## 三个入口，回答三个不同的问题

| 层 | 命令 | 回答的问题 |
|---|---|---|
| 结论层 | `frago def list` → `frago <domain> find` | 这件事已经沉淀成结论了吗 |
| 产物层 | `frago context data:<关键词>` | 上次那份东西落在哪个目录 |
| 过程层 | `frago session search "<一句话>"` | 当时怎么做的、为什么这么定、用户原话是什么 |

**三个入口不互相替代，查了一个不等于查过了。**

过程层是唯一记着"为什么"的地方。结论层只有结论，产物层只有成品——当时的取舍、走过的弯路、用户拍板时说的那句话，只在会话记录里。所以凡是问"为什么是这样""上次怎么办的"，过程层 MUST 查。

`frago session search` 会让模型把一句话摊成十来个字面量关键词，再 ripgrep 扫 `~/.frago/sessions`（claude 和 opencode 两个库、含 Claude 已滚删的老会话）。一句自然语言就够，不用自己想关键词。心里已经有确切字眼时用 `--terms` 直接给，省掉模型那一轮。

## 什么时候 MUST 召回

- 任务里出现一个**具名的机器、环境、服务、项目、客户**（ali、box、某台服务器、某个仓库、某家公司）——名字背后的事实你一定不知道
- 你要陈述一个"这里是怎么做的"的方案，而依据**全部来自读代码**
- 用户说"上次""之前""那次""原来"
- 用户否掉了你的结论，让你"自己研究"——他指认的就是你缺历史，不是缺代码理解
- 你正要说"我不记得了""看起来应该是""一般来说"

## 反模式：一次真实的翻车

用户说"更新 ali 上的 frago"。agent 跑了二十多次工具调用——ssh 探机器、读 `launch_guard.py`、读 `server_command.py`、翻 PyPI——推出"用 `uv run frago server restart`"。被否。再读三个文件，还是这条。第二次被否。

正确答案是 **ali 是部署机，部署机走 `frago update --repo`**；`uv run frago server restart` 是开发机把未提交改动打包上线的通道，在部署机上用只会凭空造一个 git 里不存在的版本号、并把工作区弄脏。

"部署机 vs 个人机"这个分别，两周前的会话里就写着。ali 的登录方式和 `sudo -u frago`，另一场会话里写着。**全程一次 `frago session search` 没跑。**

推理推得再细也到不了那儿——代码里没有"ali 是部署机"这句话。

## 召回完要闭环

这一轮现学到的本机事实（这台机器怎么装的、这个流程为什么这么定），MUST 沉淀进对应知识域，见 `frago book frago-principle-extend`。不沉淀，下一场会话原样重来一遍。
