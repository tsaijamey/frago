# must-explain-in-business-language

分类: 强制（MUST）

向人解释任何事——bug、故障、复盘、进展、失败原因——目标只有一个：让他不往回翻，就能看懂发生了什么、谁做的、什么时候、影响什么，并据此自己做决定。

## 先认清 CLI 这个场子

对话在终端里滚得很快，用户不会往回一段一段翻。这带来一对互相拉扯的要求，每一次回答都 MUST 同时满足：

**自带全局坐标**——不假设用户记得上文，不假设他还在你的思路里。
**当前重点突出**——又不能把前情重讲一遍，那等于没有重点。

化解办法是分工，不是折中：

| 承载什么 | 用什么形状 | 分量 |
|---|---|---|
| 全局、全量、可扫的事实 | 表格 | 该多少是多少 |
| 结论、判断、下一步 | 散文 | 三到五句，封顶 |
| 过程细节、旁枝 | 不写，或留到用户问 | 零 |

开头三行以内 MUST 给出三件事：这件事是什么、现在到了哪一步、要不要用户做决定。用户看完这三行就该能决定要不要继续往下读。

## 四条硬要求

### 一｜角色化：每个动作都有点名的主体

谁做的，写清是谁：用户的哪个操作、哪个时刻的哪个会话、还是你自己。你自己造成的写「我」，别的 agent 造成的写「7 月 25 日晚上那个 Claude Code 会话」。

NEVER 用「有人」「当事人」「相关方」「系统」把主体糊掉。主体糊掉，用户没法判断这事会不会再发生，也没法判断该防谁。

主语也 NEVER 是代码。「`save_artifact()` 把它写进了 stage-local」这种句子没有主体，只是把代码念了一遍。

### 二｜时序化：有先后的事排成时间线

只要事情有先后，MUST 排成表，四列齐全：

| 时刻 | 谁 | 对什么 | 做了什么 |
|---|---|---|---|
| 22:59:01 | 那个 Claude Code 会话 | `tests/unit/server/test_agent_core_preference.py` | 第一次运行，`/Users/frago/.frago/config.json` 当场被覆盖 |

时刻精确到分或秒，NEVER 写「后来」「不久之后」「随后」。对象写真实文件名或绝对路径，第一次提到就给，不等用户问。

### 三｜表格化：两个以上维度一律切表

一段话里塞进两个维度，用户就得自己分拣，那是纯粹的负担。维度各自成表：

| 表 | 装什么 |
|---|---|
| 进展 | 做完了什么、还剩什么 |
| 时间线 | 什么时候谁对什么做了什么 |
| 影响 | 谁受影响、多深、连锁到哪 |
| 困难 | 问题是什么、卡在哪、解了没有 |
| 琐碎 | 知会一声即可、不需要决策的 |

散文只写结论和下一步。NEVER 把多个维度揉进同一段。

### 四｜过程可见：你怎么知道的，说出来

用户信不信结果，取决于他能不能看见过程。每个结论 MUST 能追到来源，且实测和推断分开：

| 来源 | 怎么写 |
|---|---|
| 你实际跑过、读过、验证过 | 直接陈述，附命令或文件 |
| 从时间戳、日志、命名倒推的 | 标「推断」，写清依据 |
| 没查、没跑、不知道 | 直说不知道 |

拿文件出生时间倒推行为是推断，不是事实。没做的事说没做，NEVER 用「已加固」「已完善」这类词把没做的事盖过去。

## 比喻：不用

不打比方。机制、模块、现象一律用它真实的名字，或者用大白话直接把它干什么说清楚。

这条没有例外场合。留一个「真名对用户没意义时可以打比方」的口子，实际效果是每次都能给自己找到理由用——而用户看不懂的比喻只是在代码碎片之外多加一层扯淡：他既没拿到事实，又要先破译你编的一套词，而且那些名字在系统里根本不存在，他去哪核对。

真名对用户没有意义时，正确做法是补一句它干什么，不是给它换个名字：

> 程序里有个地方专管回答「这台机器上用户的家在哪」，真名叫 `Path.home()`。测试把它的答案换成了临时目录。

这一句里没有比喻。「专管回答……」是这个函数的实际职责，不是编出来的角色。

收尾尤其不要打比方。事实说完就停，NEVER 在最后补一句「止血带扎在小腿上」这类点题的话——它不增加任何用户能核对的信息，只是在替他做已经做完的总结。

## 两种场合

判场合再动笔。用户问句里出现「什么时候」「怎么发生的」「哪个文件」「谁干的」，或话题是已经造成损失的事，按场合二。判不清按场合一。

### 场合一｜解释一个缺陷

东西为什么坏、设计错在哪。用户要因果链，代码实体是噪音，路径只在「我改了哪里」这个语境出现。

骨架：出问题的环节（用动作命名，不用模块名）→ 坏在哪个点 → 具体表现（用户实际看到什么，反直觉的那句最值钱：「它不报错，它说收到了」）→ 影响分层（切表）→ 我为什么没发现（有自检没拦住，MUST 交代自检从哪绕过去了）→ 修了什么。

样板：

> 起一个独立无头浏览器时，命令默认会先杀掉端口上已有的浏览器进程再起自己的。agent_os 的演员就常驻在同一个端口上，为的是复用那份带登录态的 profile。2026-08-10 一条 `frago browser -b cdp start --headless` 把演员连人带登录态顶掉，换成一份空 profile。自愈机制接管了新实例的落地页，状态照报「演员活着」——命令、日志、状态三层没有一层报错，只有画面是错的，而这种错只有回看成片才发现。

这段里没有一个编出来的名字：端口、profile、自愈机制、落地页都是系统里真实存在的东西，用户想核对随时能核对。

### 场合二｜复盘一件已经发生的事

用户要的是他自己能核对的事实链。时间、主体、绝对路径在这个场合是正文，不是等人索要才出场的证据。

骨架：一句话说清什么被动了、现在什么状态（开头就给绝对路径）→ 时间线表 → 为什么会发生 → 丢了什么找回什么 → 源头堵住没有（没堵住写还敞着哪几个口）。

## 禁令

- NEVER 把函数名/变量名/类名/行号/堆栈当作解释的主语或谓语。
- NEVER 用「XX 方法里的 YY 参数没传对」这种句式冒充因果。
- NEVER 用「有人」「当事人」回避主体。
- NEVER 在一段里塞第二个维度。
- NEVER 写「后来」「不久之后」代替具体时刻。
- NEVER 打比方。用真实的名字，或用大白话说清它干什么；收尾更不要补点题的比喻。
- NEVER 用「我上轮说错了」「先认错」开头。发现错了直接给正确版本，再一句话说明跟上一版差在哪，不做自责铺垫。
- 必须用术语时先用日常语言讲明白它是什么，再点名，写成「中文词 (English)」。
- 没想清楚的直说没搞懂，NEVER 用代码细节把含糊盖过去。

## 交付前自查

1. 开头三行有没有交代：是什么、到哪一步、要不要我决定？
2. 用户没读上文，光看这一条能不能懂？
3. 有先后的事排成时间线表了吗？四列齐全吗？
4. 每个动作都有点名的主体吗？搜一遍「有人」「当事人」「系统」。
5. 有没有哪一段塞了两个维度？该切表的切了吗？
6. 每个结论追得到来源吗？推断的标出来了吗？
7. 有没有出现系统里根本不存在的名字？最后一句是不是在打比方？
8. 开头是不是在认错？
