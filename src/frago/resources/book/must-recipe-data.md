# must-recipe-data

分类: 替代（MUST）

## 解决什么问题

配方自己决定把数据写在哪。平台起进程时会交代「这次运行为谁而跑、数据放哪」，
但配方普遍写成「平台给了就用，没给就用我自己的默认路径」。于是同一份数据在
一台机器上散成好几份，各自演化，谁也不知道哪份最新，而且**任何一份都不会报错**。

本机上实测：300 个配方里 184 个会落盘，其中只有 4 个真正只认平台交代的落点。

### 写错了会发生什么

一本 A 股交易账本，在一台服务器上散成了四份：

| 内容 | 笔数 | 最后成交 | 在哪 |
|---|---|---|---|
| 录入页记的（最新） | 48 | 08-24 | 那个人自己的账户目录 |
| 「主人」那份 | 45 | 08-21 | 一个跟人无关的共享缓存目录 |
| 查看页的快照 | 45 | 08-21 | 同一个人的另一个配方目录 |
| 工作目录残留 | 37 | 08-14 | 某次运行的临时落脚点 |

人在录入页记了三笔，回到查看页数字没变。**页面每次「刷新」都报成功**，因为它
刷的是自己那份快照，而那份快照的来源已经不再更新。这类错误查起来极贵：要逐个
文件算指纹、比时间戳，才能拼出哪份是真的。

## 唯一落点

    <根>/recipe-data/<配方名>/                          单例配方
    <根>/recipe-data/<配方名>/projects/<项目名>/        多份配方

`<根>` 是**这次运行属于谁**，本机与服务器完全一致：

    ~/.frago/users/<身份id>/recipe-data/...

每一份活的目录里有一个保留文件 `state.json`——配方跑完留给页面的那张便条，由平台写。
**配方 NEVER 自己写这个文件名**，要发布状态走 `frago recipe publish`。

便条放在它描述的那个目录里，不另开一棵树：这样「便条属于哪份活」由结构本身保证，
不靠人记得对齐。上面那本账散成四份，根子就是便条按一套键归档、数据按另一套键归档。

### 单例还是多份

**由配方在元数据里显式声明，NEVER 靠推断。**

- **单例**：这个配方一辈子只维护同一份数据，再跑一次是更新它。行情缓存、账本。
- **多份**：每次接的是一件互不相干的活，各有各的数据。视频制作、每一局训练、每一次回测。

判据：**同一个人这个配方的第二次运行，需不需要和第一次的数据并存？**
需要就是多份，不需要（第二次就是覆盖第一次）就是单例。

不声明的下场是现成的：本机有个回测配方开了两个「项目」，两边的数据目录写的是
同一个路径。平台以为是两份活，磁盘上是一份，互相覆盖，不报任何错。

## 跨用户共用的数据

放在机器级，不在任何人的树下：

    ~/.frago/recipe-data/<配方名>/share/seed/      起步数据
    ~/.frago/recipe-data/<配方名>/share/common/    共读数据

两者性质相反，**必须分开**：

- **起步数据**：新用户第一次跑时复制一份给他，从此归他，他改他的，原件再更新与他无关。
- **共读数据**：所有人读同一份，谁跑谁更新。**NEVER 复制**——一复制就是 N 份各自过期
  的数据，而且没人知道哪份对。

### 判据只有一句

> **复制之后，原件还会不会继续更新。会，就不能复制。**

这条要在写配方之前问一遍。判错不会报错，只会在半年后表现为「两个人看到的数字不一样」。

体积也走这条：**凡是「复制一份给每个用户会让你心疼」的东西，它本来就不该是起步数据。**
有些磁盘支持「复制后不额外占空间、改了才真的分家」的复制方式，但**不能依赖它**——
实测本机 APFS 支持，一台 ext4 的服务器不支持，那上面复制就是实打实占空间。

共读数据靠**平台在起进程时多交代一个只读目录**告诉配方，NEVER 用软链接或硬链接：

- 硬链接的后果取决于配方怎么保存文件——「写临时文件再顶替」会断开链接变成两份，
  「原地改」会穿透污染所有人。同一个动作两种相反结果，从目录结构上看不出会是哪一种。
- 软链接只说明位置，说明不了谁能写。而共读数据的核心约束正是「所有人读、只有一个
  配方能写」。想用文件权限兜底也兜不住：一台机器上所有用户共用同一个系统身份。

## 运行必须绑定用户

**每次运行都绑定到一个身份，绑不上就拒绝运行。没有「没有归属」这种状态。**

- 本机：安装时静默生成一个身份记下来，用户什么都不用做。此后这份记录缺失或读不出
  就是异常，**报错，NEVER 临时造一个顶上**——那个兜底分支会在半年后变成第二个默认路径。
- 服务器：绑到触发这次运行的那个登录用户。
- 定时任务、后台运行这类没有触发者的：绑到这台机器记录的默认用户，并且**记录里要有
  这个字段**。不写进去，下一个做定时任务的人会再发明一次默认值。

身份属于**人**，不属于机器——一个人可能装在笔记本、台式机、服务器上，按机器发身份
等于把他变成三个人，数据搬过去认不回来。所以身份要能导出、导入。

### 「主人」不是一个数据持有者

运维权限（启停服务、改配置、看日志）和数据归属是两件正交的事。运维一台 frago 的人
不自动等于上面某个用户，**运维权限不隐含数据可读**。运维者当然能用 `cat` 去读磁盘，
那归操作系统管；但 **frago 自己的任何一个入口都不提供越过归属的读法**。

## 配方作者要做的

一句话：**不要自己拼数据路径**。

```python
# ❌ 错：平台没给就用我自己的——所有事故的入口都是这一句
DEFAULT_DIR = Path.home() / ".frago" / "data" / "etf" / "recipe-caches" / "my-recipe"
data_dir = Path(os.environ.get("FRAGO_RECIPE_DATA_DIR") or DEFAULT_DIR)

# ✅ 对：只认平台交代的落点，没有就是异常
data_dir = Path(os.environ["FRAGO_RECIPE_DATA_DIR"])
```

NEVER 改成 `import frago`：带 PEP 723 块的配方跑在隔离环境里，import 不到。

## 与 must-data-dir 的分界

两套目录，各管各的，**永不混**：

| | 给人翻的 | 给机器读的 |
|---|---|---|
| 内容 | 报告、看板、笔记本这类交付物 | 配方的工作数据：账本、缓存、中间态 |
| 落点 | `~/.frago/data/<主体>/<YYYYMMDD>-<slug>/` | `<根>/recipe-data/<配方名>/...` |
| 归档键 | 主体（客户、产品、领域） | 配方 |
| 带日期 | 是 | 否 |

判据是**谁会去翻它**。人翻的按主体归档，机器读的按配方归档。

配方的工作数据 **NEVER 再往 `data/<主体>/recipe-caches/` 下放**——那是本条生效之前的
老落点，正在迁走。「主体」这一维在配方工作数据这一侧是冗余的：一个 ETF 账本配方
底下再开一个叫 `etf` 的目录，说明不了任何事。同一个配方要服务第二本账，那是**项目**，
不是主体。

## 名字

叫 `recipe-data` 不叫 `recipe-caches`。用户那本账不是缓存，丢了就真没了；
叫 caches 会让写磁盘清理脚本的人看到 `*-caches` 就敢删。
